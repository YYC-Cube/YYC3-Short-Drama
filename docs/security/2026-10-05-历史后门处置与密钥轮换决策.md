## 三、决策

### D1：永久禁止从 git 历史原样恢复 /app/api/（已执行）

- `next.config.mjs` 头部注释中的恢复指引已替换为安全警告并指向本文档。
- `.gitignore` 中 `/app/api/` 条目的注释同步改为警告。
- **规则**：恢复全栈能力必须基于干净重写的 API 路由 + `lib/jwt-config.ts` 式强制环境变量校验；重写时参考历史实现的业务逻辑可以，复制代码不行（尤其鉴权路径）。

### D2：git 历史改写延后为 Owner 手动操作（决策：不做自动化执行）

**理由**：
1. 当前利用风险为零（见暴露面评估），不属于紧急操作；
2. 历史改写（filter-repo）会使全部 commit SHA 失效，影响：dependabot 分支、本地工作树、外部 fork/clone 的协同；
3. GitHub 服务端仍保留旧对象（dangling commits 可通过 SHA 访问），彻底清除需要向 GitHub Support 提交 GC 请求——该步骤只有仓库 Owner 能做；
4. 强制推送公共 main 属于不可逆操作，应由 Owner 在知情状态下执行。

**Owner 执行手册**（当决定清除历史时按序操作）：

```bash
# 0) 前置：通知所有协作者；确认无进行中的 PR（关闭 dependabot PR #1）
# 1) 安装工具
brew install git-filter-repo
# 2) 镜像克隆（勿在原工作树操作）
git clone --mirror git@github.com:YYC-Cube/YYC3-Short-Drama.git
cd YYC3-Short-Drama.git
# 3) 移除历史中的 API 路由路径（含后门代码）
git filter-repo --path app/api --invert-paths
# 4) 强制推送全部分支/标签
git push --force --all && git push --force --tags
# 5) 向 GitHub Support 提交请求：清除悬空对象/缓存视图（附仓库与受影响 SHA）
# 6) 所有协作者重新 clone（旧 clone 的 SHA 已失效）
```

**替代方案（不改写历史）**：若 Owner 接受"历史仅作考古用途"，可保持现状——本决策 D1 已消除误恢复路径，且当前部署不可利用。
